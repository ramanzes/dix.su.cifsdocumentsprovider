# v2.4.0-dixsu.15 — бэкап на медленные SFTP-хосты больше не зависает

| | |
|---|---|
| Дата | 2026-10-22 |
| Версия | `2.4.0` (versionCode 32), тег `v2.4.0-dixsu.15`, коммит `5771df7` |
| Предыдущая версия | [v2.4.0-dixsu.14](https://github.com/ramanzes/dix.su.cifsdocumentsprovider/releases/tag/v2.4.0-dixsu.14) |
| APK | [CIFSDocumentsProvider-2.4.0-dixsu.15-release.apk](https://github.com/ramanzes/dix.su.cifsdocumentsprovider/releases/tag/v2.4.0-dixsu.15) |
| Подпись | production-ключ dix.su (CN=dix.su, SHA-256 `f42dec9c…adcc326`), не debug |

Этот релиз завершает серию исправлений бэкапа на WD My Cloud и другие медленные SFTP-хосты
(dixsu.13 → dixsu.14 → dixsu.15). Кого касается: всех, кто пользуется встроенным бэкапом —
**«Sync now»** и **«Auto backup»** (оба идут через один и тот же код).

## Коротко

- **Исправлено зависание «Sync now» навсегда** после нескольких файлов. Это и была настоящая
  причина «синк висит часами» — взаимная блокировка внутри SFTP-библиотеки, а не медленная сеть.
- **Проверка уже загруженных файлов стала быстрее**: один листинг на удалённую папку вместо
  листинга на каждый файл.
- **Оборванная загрузка докачивается**: файл пропускается, только если на сервере есть файл с тем
  же именем **и тем же размером**.

## Предыстория: три релиза одной проблемы

Исходная жалоба: на соединении с WD My Cloud (ARMv7, Debian 7, старый sshd с одними `ssh-rsa`/
`ssh-dss`, доступ через dixsu-туннель `admin-dixsu-mycloud`) «Sync now» сначала вешал приложение
с диалогом «isn't responding», а потом просто не двигался часами.

| Версия | Коммит | Что исправлено |
|---|---|---|
| dixsu.12 | `e2ab5c4` | последняя версия до исправлений |
| dixsu.13 | `2f1b475` | ANR: проверка файлов шла на главном потоке. Перенесена на IO-диспетчер (`withContext(dispatcher)` в `SendRepository`) |
| dixsu.14 | `892fa6d`, `dea2817` | SSH keepalive, чтобы NAT и туннель не обрывали простаивающее соединение |
| **dixsu.15** | `5771df7` | **deadlock VFS**, один листинг на папку, докачка по размеру |

После dixsu.13 диалог ANR пропал, но синк всё равно мог стоять. Изначальная гипотеза (ТЗ
`ANR_FIX_TZ.md`) — «проверка просто медленная: на каждый файл полный листинг папки, 10 000 файлов
× 1–2 с = часы». Это правда, но тест на реальном устройстве показал, что главная причина другая:
синк вставал **навсегда** уже на 3–4-м файле из 50, а сеть при этом простаивала.

## 1. Взаимная блокировка (deadlock) в Apache Commons VFS

### Симптом

«Sync now» загружает несколько файлов и останавливается. Прогресс не меняется, ошибок нет,
трафика нет. Помогает только убить приложение.

### Причина

Подтверждена дампом потоков (jdb) на BlissOS во время зависания. Два потока ждут друг друга:

```
Поток A (закрытие только что загруженного файла)
  ApacheProxyFileCallback.onRelease → фоновый close()
  → SftpFileObject.endOutput → onChange → statSelf()    держит: монитор ФАЙЛА
  → SftpFileSystem.putChannel()                         ждёт:   монитор ФАЙЛОВОЙ СИСТЕМЫ

Поток B (листинг папки для следующего файла)
  queryChildDocuments → AbstractFileSystem.resolveFile() держит: монитор ФАЙЛОВОЙ СИСТЕМЫ
  → AbstractFileObject.doDetach()                       ждёт:   монитор ФАЙЛА
```

VFS везде берёт блокировки в порядке «файловая система → файл», кроме собственных
`synchronized`-методов `SftpFileObject` (например `statSelf()` при закрытии потока записи) —
они берут сначала файл. Приложение закрывает записанный файл в фоне (`onRelease` →
`launch { close() }`), и в это же время отправка следующего файла листает ту же папку. Если
закрытие медленное (как на My Cloud через туннель), шанс попасть в эту гонку высокий; на быстрых
хостах закрытие мгновенное, поэтому баг почти не проявлялся.

### Исправление

`data/storage/apache/.../ApacheProxyFileCallback.kt`: все операции с файлом — чтение (`onRead`),
запись (`onWrite`), закрытие (`closeReader`/`closeWriter`) и получение размера — выполняются под
монитором файловой системы:

```kotlin
private inline fun <T> lockFileSystem(block: () -> T): T {
    return synchronized(fileObject.fileSystem) { block() }
}
```

Теперь порядок блокировок везде одинаковый (ФС → файл), и цикл ожидания невозможен. Цена —
операции над разными файлами одного соединения выполняются по очереди, но SFTP-сессия у VFS и
так одна на соединение, поэтому на скорость это практически не влияет.

## 2. Один листинг на папку

### Было

- `sendFolderSkippingExisting` для каждого файла вызывал `existsFile()` → `DocumentFile.findFile()`
  — это **полный листинг удалённой папки на каждый файл**.
- `collectRecursive` для каждой подпапки вызывал `findFile()` — ещё по листингу.
- Вдобавок `DocumentFile.listFiles()` делает отдельный запрос к провайдеру на каждое имя, тип и
  размер каждого ребёнка.

### Стало

`data/storage/manager/.../DocumentFileManager.kt`, новый `queryChildren(dirUri)`: один
`contentResolver.query` на `buildChildDocumentsUriUsingTree` сразу с колонками `DOCUMENT_ID`,
`DISPLAY_NAME`, `MIME_TYPE`, `SIZE`. Используется в двух местах:

- `collectRecursive` — листинг целевой папки берётся лениво и один раз, по нему ищутся
  существующие подпапки; недостающие создаются через `DocumentsContract.createDocument`.
- `listFileSizes(dirUri)` — имя → размер файлов в папке; `SendRepository` кеширует его по
  целевой папке (`existingByDir`).

Итог: число SFTP-листингов пропорционально числу **папок**, а не файлов. Для 10 000 файлов в
250 папках — около 250 листингов вместо ~10 000.

## 3. Пропуск по имени и размеру (докачка)

### Было

Файл пропускался, если на сервере есть файл с тем же именем и ненулевым размером
(`exists() && length() > 0`). Первый вариант dixsu.15 из ТЗ проверял вообще только имя.

### Проблема

Если загрузка оборвалась (приложение убито, пропала сеть, сел телефон), на сервере остаётся
**частичный** файл — с правильным именем и ненулевым размером. Такой файл пропускался бы при
каждом следующем Sync навсегда, то есть в бэкапе оставалась бы битая копия.

### Стало

`SendRepository.sendFolderSkippingExisting`: файл пропускается, только если на сервере есть файл
с тем же именем **и тем же размером**, что у локального. Иначе он загружается заново, и копия на
сервере перезаписывается.

> **Изменение поведения.** Если локальный файл изменился и его размер стал другим, он тоже будет
> загружен заново и перезапишет копию на сервере. Для бэкапа это ожидаемо, но раньше
> существующие файлы не перезаписывались никогда. Файл, изменившийся без изменения размера,
> по-прежнему не перезагружается.

Остальные пути отправки («Поделиться → сохранить в это приложение») не изменились.

## Проверка

Сборка: release, установлена на BlissOS (Android 13 x86_64, VM). Соединение — SFTP через
dixsu-туннель к WD My Cloud. Локальная папка `fortest` (50 файлов в 5 папках, в том числе пустая
папка и вложенность в 2 уровня) → удалённая `/DataVolume/shares/blissos/`.

| # | Сценарий | Ожидание | Результат |
|---|---|---|---|
| 1 | Первый Sync | все файлы загружены, без зависаний и ANR | ✅ до исправления deadlock — вечное зависание на 4-м файле; после — все файлы за ~1,5 мин |
| 2 | Повторный Sync | 0 файлов в очереди за секунды | ✅ 0 файлов, проверка ~7 с (7 листингов) |
| 3 | +3 новых файла (корень, вложенная папка, бывшая пустая папка) | загружены ровно эти 3 | ✅ |
| 4 | Обрыв посреди загрузки 8 МБ файла (force-stop на 50 %) | файл загружен заново целиком, следующий Sync — 0 | ✅ |
| 5 | Force-stop через 3 с после Success | файл на сервере целый, следующий Sync — 0 | ✅ |
| 6 | Release-сборка с нуля: новое соединение, +2 файла (4 МБ и текстовый) | загружены оба, следующий Sync — 0 | ✅ |

Одно наблюдение без окончательного объяснения: сразу после перезагрузки устройства (шаг 4) докачанный
файл был загружен ещё раз при следующем Sync, повторить это не удалось. На целостность это не
влияет — при несовпадении размера файл просто загружается заново.

## Известные ограничения

- **Не убивайте приложение посреди загрузки.** Приложение пишет файл через собственный
  DocumentsProvider (FUSE). Если убить процесс в этот момент, он может остаться «зомби», и
  приложение не запустится до перезагрузки устройства. Останавливайте загрузку кнопкой
  **Cancel**.
- **Подсказка в интерфейсе устарела**: в секции Backup по-прежнему написано «Upload new files
  (by name)», хотя теперь сравниваются имя и размер. Будет исправлено в следующей версии.
- **Debug-сборки пишут приватный ключ в logcat** (через `toString()` соединения в `logD`). В
  release логирование отключено, поэтому для пользователей release-APK это не актуально. Для
  разработчика: после отладки на устройстве очищайте logcat (`adb logcat -c`).
- **Таймаут SFTP** фиксирован (10 с, `CONNECTION_TIMEOUT`); на совсем медленных хостах может не
  хватать. Не менялся в этом релизе.

## Справка: SSH keepalive (dixsu.14)

Описание в ТЗ устарело, правильное поведение такое (`ApacheSftpClient.kt`,
`KeepAliveConfigRepository`):

- `getHostname()` возвращает `null`. Любая не-null строка, даже `""`, **заменяет** хост сессии
  в JSch — в исходной версии (`892fa6d`) из-за этого все SFTP-сессии шли на localhost.
- `ServerAliveInterval` не задаётся: JSch принимает его в миллисекундах и вызывает `setTimeout`,
  который VFS всё равно перезаписывает таймаутом сессии (10 с).
- Задаётся только `ServerAliveCountMax = 3`: keepalive уходит каждый раз, когда истекает таймаут
  сокета (10 с простоя), после 3 keepalive без ответа соединение разрывается с ошибкой вместо
  вечного зависания.

## Установка и обновление

- Обновление поверх dixsu.12–14 (подписаны тем же ключом) сохраняет соединения и настройки.
- Поверх сборки, подписанной другим ключом (debug, оригинальный wa2c), установка невозможна —
  нужно удалить старую версию, и соединения придётся создать заново.
- Сборка из исходников (без ограничения памяти Gradle на машине с малым ОЗУ процесс убивается с
  exit 137):

  ```bash
  ./gradlew assembleRelease --no-daemon --max-workers=1 \
    -Pkotlin.compiler.execution.strategy=in-process \
    -Dorg.gradle.jvmargs="-Xmx2560m -XX:MaxMetaspaceSize=768m"
  ```

  Подпись — через `keystore.properties` (см. `keystore.properties.sample`).
